# 設計判断の記録（ADR）

正本: `docs/00-master.md` / 展開: `docs/prd/tegata-credits.md` / 規範: `spec/`

各 ADR は「後から覆すと高くつく判断」だけを記録する。実装の細部は PRD 側に置く。
すでに確定した判断は下表の通り。詳細は参照先に本文がある。

| # | 判断 | 理由（要約） | 参照 |
|---|---|---|---|
| D-01 | 推論をプロキシせず、SDK が実測値を capture で送る | プロキシ化はレイテンシ・可用性・データ処理同意の責任を全部引き受けることになり、「落ちたら顧客が止まる」リスクを最大化する | PRD §7.6 |
| D-02 | 不渡りは HTTP 402 ではなく 200 + `decision` で返す | 402 は汎用クライアントで例外扱いされリトライループを招く。不渡りは異常系ではなく正常な業務判断結果 | spec/authorization.md §4.1 |
| D-03 | degraded の既定は `allow`（provisional 発行 + 事後 reconcile） | TEGATA の障害で顧客の収益機会を止めるほうが、取りこぼしより高くつく。フェイル挙動は事故ではなく宣言された設定にする | PRD §8.3 / spec/authorization.md §7 |
| D-04 | クレジットは整数。売価ペグはテナント設定、端数は常に切り上げ | 浮動小数と丸め差異による台帳不整合を構造的に排除する | PRD §5.1 |
| D-05 | 売価（クレジット）と原価（μUSD）を同一エントリ内の別列として持つ | 粗利はこの2つの差。1つの数値に混ぜた時点で margin dashboard が成立しなくなる | spec/register.md §2 |
| D-06 | 残高は単一の数値ではなく entitlement のスタック | 「サブスク分を先に、トップアップは後」「期限が近いものから」を決定的な順序で表現するため | PRD §5.1 |
| D-07 | Register は追記専用。訂正は `adjust` の追記で行い、UPDATE/DELETE を物理的に禁止 | 編集できる台帳は記録ではなく報告書。第三者がオフラインで検証できることが購買理由になる | spec/register.md §3, §5 |
| D-08 | capture は face_value 超過でも必ず成功させる | 実行はもう終わっている。拒否しても不正確な台帳が残るだけで、overdraft のほうがまだ健全 | PRD §7.7 / spec/authorization.md §4.2 |
| D-09 | トップアップ収益は購入時ではなく消費時に認識する | 購入時認識だと「大量購入して使わないユーザー」が高粗利として現れ、赤字ユーザー検出の信号を汚す | PRD §11.2 |
| D-10 | ポリシーは交差で合成する（override を持たない）。最も厳しい結果が勝つ | override を許すと「どの規則が効いているか」が読めなくなり、監査に耐えない | spec/policy.md §3.1 |
| D-11 | 介入ルールは既定でホールドアウト群を持つ。効果測定なしのルールは作らせない | 介入が効いていることを示せることが、このデータループの価値の証明そのもの | PRD §10.4 |
| D-12 | `endorsement_chain` を Credits v1 で使わないが、スキーマ上の場所は今切る | 今日書かれた台帳が、裏書を使い始めた後も読めるようにするため | spec/authorization.md §6 |
| D-13 | Wallet は資金の保管・移動・カード発行の当事者にならない。orchestration と enforcement に徹する | ライセンス業務を持った瞬間、この事業は別の事業になる。機能追加の圧力がかかっても動かさない一線 | Wallet PRD §1.2, §12 |
| D-14 | Wallet の degraded 既定は `deny`（Credits の `allow` と逆） | 受け取る側は「顧客のプロダクトを止めない」が優先、払う側は「判断できないまま金を出さない」が優先。非対称は意図的 | Wallet PRD §7.2 |
| D-15 | Wallet は Observe → Gate → Card ASA の順で提供する | Card ASA を先に出すと発行パートナー契約が導入の前提になり、営業サイクルが伸びる。Tier 0 は導入リスクゼロで可視性を返す | Wallet PRD §6 |
| D-16 | `drawer`（責任を負う人間）を必須にし、空を許さない | 責任の所在が空欄の支出は監査に耐えない。finance に売れる唯一の理由がこれ | Wallet PRD §5.2 |
| D-17 | エージェントの失効は下流の裏書すべてを同時に失効させる。部分的失効を持たない | 下流だけ生き残る状態は、攻撃者が望む状態そのもの | Wallet PRD §5.3 |
| D-18 | margin 診断ツールはデータをサーバーに送らない。ブラウザ内で完結させる | 最大の障壁は「課金データを見知らぬスタートアップに渡すこと」。技術的に不可能な設計にすれば障壁が消える | gtm/margin-diagnostic.md §2.1 |
| D-19 | ヒアリングの合格ラインを実施前に確定させる | 事前に不合格条件を決めないヒアリングは、必ず「手応えはあった」という結論になる | gtm/icp-interviews.md §0 |
| D-20 | 保留（issue）は残高を動かさない。残高が動くのは約定（grant/capture/adjust/entitlement失効）のみ | 保留を残高移動として記録すると `available = balance − reserved` が二重計上になる。約定と約束を同じ列に混ぜない | spec/register.md §3–4 |
| D-21 | ハッシュは「hash 列を除いたエントリ全体の JCS」に対して1回だけ定義する。`prev_hash` はエントリの中に置く | 連結とフィールドの二重定義は実装ごとの解釈差を生む。サンプル台帳は実際に検証可能なテストベクタとして保守する | spec/register.md §5 |
| D-22 | 非金銭の監査事象（割印の承認/却下、失効、停止）は `kind=event` で記録する。`adjust` を流用しない | `adjust` は訂正の意味論を持つ。承認は訂正ではない。意味論を混ぜた台帳は監査で説明できない | spec/register.md §3 |
| D-35 | 診断ツールの「送信しない」を `_headers` の `connect-src 'none'` で**強制**する。ページ上の主張に留めない | 「送信しません」と書いたページと、送信できないページは別物。ここを緩めるとあのツールの存在理由が消える | plan/deploy.md §2 |
| D-34 | webhook は署名検証を**必須**にする。secret 未設定・署名欠落・未知テナントはすべて 401 で、応答を区別しない | 「署名があれば検証する」は、署名を付けなければ検証されないということ。この経路はクレジットを発行するので、通してよい要求は署名されたものだけ | plan/security-review.md S-01 |
| D-32 | GTM Prototype gate の**ヒアリング条件を外す**。gate は「ローンチ動画を作って出せるか」に一本化する | オーナー判断（2026-08-21）。市場は確定と見なす。ヒアリングは検証手段であって目的ではなく、確信があるなら検証に時間を使う理由がない | 00-master.md §6.1 |
| D-33 | Q-04（価格）と Q-05（Stripe のみ）を**検証済みの結論ではなく、明示された前提**として確定する | D-32 でヒアリングを外した以上、この2つに根拠は付かない。「未検証の前提」と書いておけば、外れたときに何を疑うべきかが分かる。未決のまま放置するより良い | 00-master.md §6.3 |
| D-31 | 性能は単一の並列度・単一実行での合否ではなく、**並列度ごとの曲線と成立範囲**で報告する。計測時間も明記する | 選び方次第で合否がどうとでもなる。実際、同じコードで12秒計測なら「50接続まで合格」、60秒計測なら「25接続まで」になった。厳しい方を正式値とする。100接続の p99 87ms は単一ライタへの待ち行列であって処理コストではない | plan/perf/authorize.json |
| D-30 | Credits MVP の実装を gate 判定と並行させる。Wallet は実装しない | ローンチ動画の拍2/拍3 は実装なしに撮影できず、gate と MVP が循環依存になった。Wallet は市場が EARLY と実証済み（D-26 の調査）なので A→B 順序を維持する | 00-master.md §6.0 |
| D-29 | core は I/O・wall-clock・乱数を持たない純粋層とし、Clock/Rng を注入する。禁止パターンを CI で機械検査する | 決定論なしに INV-1〜11 はテスト不能。分散化の際に core を書き直さないための唯一の防衛線 | plan/credits-mvp.md §2.1–2.2 |
| D-28 | MVP の degraded mode は SDK 側で実装する（server 側は provisional capture の受理と reconcile のみ） | 単一ノード MVP では「Edge が判断不能」の実体はクライアントから見たタイムアウト。分散前に server 側 degraded を作るのは実体のない抽象 | plan/credits-mvp.md §5.4 |
| D-27 | MVP スタックは TypeScript + Fastify + better-sqlite3（単一ノード）。Ajv に spec/schema をそのまま接続し、スキーマの二重定義を作らない | 同期 SQLite は subject 単位直列化が構造的に成立する。Q-03（分散 Edge 基盤）の本回答は据え置き、storage アダプタ境界で守る | plan/credits-mvp.md §2 |
| D-26 | 自分のテーゼを否定しうる**反証条件**を gate に先に書く（Product B: 「実際の失敗モードは暴走支出ではない」が過半なら不合格） | 恐怖の証言は無料で手に入り、予算は手に入らない。反証条件がないと、恐怖だけ集めて「市場はある」に着地する | gtm/icp-interviews.md §0.3 |
| D-25 | 読めなかったデータからは見出しを出さない。「Not enough to answer」と理由を返す | 0% という数字は、読めなかった原価から出た瞬間に嘘になる。除外パネルに書いてあっても、人は見出ししか読まない | gtm/margin-diagnostic.md §9.1 |
| D-24 | margin 診断ツールは「Gate 前コードなし」の例外として実装する | Master Doc §6.1 が gate 通過条件に「診断ツールを公開」を含む＝gate 判定材料そのもの。製品コードの先行実装とは区別する | tools/margin-diagnostic/ |
| D-23 | `pending_seal` を規範仕様の状態として定義し、保留中は何も予約しない。issue 呼び出しは同期でブロックしない | 承認待ちの同期ブロックは Eng の導入拒否理由になる。状態を規範に置かないと Wallet が仕様外の挙動に依存する | spec/authorization.md §3 |
