## 1. スコープ

### 1.1 一行定義

エージェント別のウォレット・仮想カード、ポリシーによる支出ガードレール、リアルタイム監査を、
**レール非依存**（x402 / ACP / AP2 / カード横断）で提供する。

### 1.2 前提となる立場

TEGATA は **orchestration と enforcement に徹する。** 資金の保管・移動・カード発行の当事者にならない。
これは Master Doc §5 Product B risk 3 に対する設計上の防衛線であり、機能追加の圧力がかかっても
動かしてはならない一線である。

| 誰がやるか | 何を |
|---|---|
| 発行パートナー（Lithic / Stripe Issuing 等） | カード発行、決済ネットワーク接続、資金保全 |
| カストディ / 決済パートナー | ステーブルコイン残高の保管、オンチェーン送金 |
| **TEGATA** | **認可するかどうかの判断、その記録、その説明** |

### 1.3 v1 に含むもの

| # | 機能 | 節 |
|---|---|---|
| B1 | Agent Identity（エージェントを主体として定義し、人間の振出人に紐付ける） | §5 |
| B2 | Observe（既存カード/請求のトランザクション取り込みと可視化）— **無料層かつ wedge** | §6.1 |
| B3 | Policy Engine（`spec/policy.md` の評価器） | §7 |
| B4 | Enforcement（カード authorization webhook / x402 ゲート / MCP 前段） | §6 |
| B5 | Approval Ladder（auto → notify → counter_seal） | §8 |
| B6 | Register（Credits と共有する追記専用台帳） | §9 |
| B7 | Spend Analytics（エージェント別・タスク別・レール別） | §10 |

### 1.4 v1 に含まないもの

- 独自レール、独自チェーン、独自トークン
- 資金移動そのもの、残高の自社保管
- 経費精算ワークフロー（領収書 OCR、仕訳、会計ソフト連携）— 人間の経費の領域は取らない
- エージェントの実行基盤・オーケストレーション

## 2. ICP とペルソナ

### 2.1 ICP

エージェントを**本番で**動かし始めた企業。従業員 50–1,000 名規模。以下の2系統。

- **(a) AI-native 企業** — agentic workflow が API課金・SaaS購買・広告出稿を自動で行い始めた
- **(b) エージェントにタスク委任し始めたチーム** — Claude Code / Cowork 等の管理者

**判別条件（これが揃っていないと売れない）**: エージェントが**すでに**何らかの支払い手段に触れている、
または触れさせようとして止まっている。「将来やるかも」は ICP ではない。

### 2.2 ペルソナと対立

Product A と違い、B は**買い手と使い手が別人**である。ここが設計を規定する。

| ペルソナ | 求めるもの | 恐れるもの |
|---|---|---|
| **Platform / Eng リード**（使い手） | エージェントを止めないこと。摩擦の少ない導入 | 承認待ちでワークフローが詰まる |
| **Finance / Controller**（買い手） | 説明できること。上限が実際に効くこと | 説明のつかない請求。監査で答えられない |
| **CISO / セキュリティ** | 権限の最小化と失効可能性 | 侵害されたエージェントが金を使い続ける |

**設計上の含意**: 既定値は Eng 側が受け入れられる緩さにし、Finance 側が締められる**余地**を用意する。
逆順（既定を厳しくして緩めさせる）にすると Eng が導入自体を拒否し、そもそも可視性が得られない。

### 2.3 ユーザーストーリー

**Finance / Controller**
- US-01: 先月エージェントが使った金額を、エージェント別・目的別に見たい
- US-02: 「このエージェントは月 $2,000 まで、SaaS と データのみ」を宣言し、実際に効かせたい
- US-03: $100 を超える支出は自分が承認したい。ただし承認待ちで業務を止めたくない
- US-04: 監査で「この支払いは誰の認可か」を聞かれたときに、1画面で答えたい

**Platform / Eng**
- US-05: エージェントに支払い手段を渡す前に、まず**観測だけ**したい
- US-06: サブエージェントに権限の一部だけを渡したい（親より広くならないことを保証したい）
- US-07: エージェントが侵害されたとき、そのエージェントの権限だけを即座に失効させたい
- US-08: 承認が必要な支出でエージェントを待たせず、後で再開させたい

**CISO**
- US-09: 権限が時間とともに勝手に広がらないことを、仕組みとして保証したい

## 3. Lexicon マッピング

Credits では未使用だった語彙が、ここで全部使われる。これが「A と B が同じ台帳に載る」ことの意味。

| 語 | 識別子 | Wallet における意味 |
|---|---|---|
| 振出人 | `drawer` | エージェントに権限を委任する人間または組織。**最終責任者** |
| 受取人 | `payee` | 支払いを受けるマーチャント / API / サービス |
| 裏書 | `endorsement` | エージェント → サブエージェントへの権限再委任。**必ず縮小方向** |
| 額面 | `face_value` | 承認された上限額 |
| 満期 | `maturity` | 権限の有効期限 |
| 割印 | `counter_seal` | 人間の承認とエージェントの要求が両方揃って初めて成立する認可 |
| 不渡り | `dishonor` | ポリシー違反・限度超過による拒否 |
| 手形帳 | `register` | 監査ログ。Credits と同一フォーマット |

**`counter_seal` の実体**: 承認ラダーの最上段。人間の承認記録とエージェントの要求記録が
同一 authorization に対して両方 register に載り、片方だけでは支払いが成立しない。
「二者が同一の証書にまたがって印を押す」という手形実務そのもの。

## 4. アーキテクチャ

```
                     ┌────────────────────────────┐
   人間（drawer）  ──►│  Policy（spec/policy.md）   │
                     └────────────────────────────┘
                                  │
     ┌────────────────────────────┼────────────────────────────┐
     ▼                            ▼                            ▼
┌──────────┐              ┌──────────────┐            ┌──────────────┐
│ Card ASA │              │ x402 / HTTP  │            │ MCP / tool   │
│ webhook  │              │ payment gate │            │ pre-hook     │
└──────────┘              └──────────────┘            └──────────────┘
     └────────────────────────────┼────────────────────────────┘
                                  ▼
                     ┌────────────────────────────┐
                     │  Register（追記専用・共有） │
                     └────────────────────────────┘
                                  │
                     ┌────────────┴───────────────┐
                     ▼                            ▼
              Approval Ladder               Spend Analytics
              （Slack / Web / API）
```

### 4.1 設計原則

1. **enforcement はエージェントの実行系の外側に置く。** プロンプトやシステム指示に依存する制約は
   制約ではない。侵害されたエージェント、あるいは単に指示を無視したエージェントに対して
   効かないものを「ポリシー」と呼ばない。
2. **Credits と同一の台帳・ポリシー文法・監査形式を使う。** 別物を作ったらこの事業は
   「2つの薄いプロダクト」になる。共有 primitive が唯一の構造的優位。
3. **どのレールも対等に扱う。** 特定レールを前提にした最適化を primitive に持ち込まない。
   Master Doc §3.3 の Switzerland position は、コードのレイヤリングで守られなければ標語に終わる。
4. **判断は常に説明可能。** 拒否したときは「どの規則の、どの条件で」を返す。§7.4。

## 5. Agent Identity

### 5.1 なぜ独立した主体が要るか

「誰が使ったか」を人間の従業員 ID で表現すると、エージェントの支出は全部その従業員の
経費として現れ、ポリシーも失効も従業員単位でしか打てない。
エージェントを主体として立て、人間を**振出人**として背後に置く。

### 5.2 モデル

| 列 | 型 | 備考 |
|---|---|---|
| `agent_id` | ULID | |
| `handle` | string | `agent:researcher-2`。register に現れる表示名 |
| `drawer` | string | 責任を負う人間または組織。**必須。空を許さない** |
| `labels` | jsonb | `team`, `env`, `system` など。ポリシーの `applies_to` が参照 |
| `status` | enum | `active` / `suspended` / `revoked` |
| `credential_refs` | jsonb | 発行パートナー側のカード ID、ウォレットアドレス等の参照 |
| `parent_agent_id` | ULID \| null | 裏書によって生成された場合の親 |

> **決定事項**: `drawer` を必須にする。振出人のいない権限を作れないようにすることが、
> このプロダクトが finance に売れる唯一の理由である。責任の所在が空欄の支出は監査に耐えない。

### 5.3 失効（US-07 / US-09）

- `agent.revoke` は当該エージェントと、**そのエージェントが裏書した下流すべて**を同時に失効させる。
  部分的失効という概念を持たない（下流だけ生き残る状態を作らない）。
- 失効は発行パートナー側のカード停止 API を呼ぶが、**TEGATA 側の判定は即座に効く**。
  パートナー API の遅延・失敗が失効を遅らせてはならない。
- 失効は register に `kind=event`（`meta.event = agent_revoked`、失効実行者と対象の下流一覧を含む）
  として記録され、以後の authorization は `subject_suspended` で不渡り。

## 6. Enforcement Point

**採用の順序がそのまま導入の順序になる。** 摩擦の低い順に3段階。

### 6.1 Tier 0 — Observe（無料層 / wedge）

既存の支払い手段（法人カード、クラウド請求、API 請求）のトランザクションを取り込み、
エージェント・タスク・目的に**帰属させて可視化するだけ**。ブロックしない。

- 取り込み: CSV / カード発行元 API / クラウド請求 API / SDK からの自己申告
- 帰属: トランザクションの説明文・金額・時刻と、エージェントの実行ログを突合。
  確度が低いものは `unattributed` として明示する。**推測で埋めない。**
- 出力: 「先月、エージェントが使った $X のうち、$Y は帰属先が特定できない」

> **これが売り物になる理由**: 導入リスクゼロで、finance が今すぐ答えられない質問に答えが出る。
> Master Doc §2.2 の wedge「エージェントに会社のカードを渡す前に読むドキュメント + 無料の
> spend visibility」の後半がこれ。

### 6.2 Tier 1 — Gate（実行前の認可）

エージェントが支払いを**要求する経路**に認可を挟む。ブロック可能。

| 経路 | 実装 | レイテンシ要件 |
|---|---|---|
| HTTP 402 / x402 | 支払い実行前の SDK / プロキシフック | p99 < 100ms |
| MCP tool 呼び出し | tool 実行前フック | p99 < 100ms |
| API 購買（SaaS 契約、クレジット購入） | SDK からの明示的 authorize | p99 < 100ms |

`spec/authorization.md` の issue / capture をそのまま使う。Credits との違いは
`face_value` の単位が通貨の最小単位であること（`currency` フィールドが付く）だけ。

### 6.3 Tier 2 — Card ASA（決済ネットワーク上の認可）

TEGATA 経由で発行された仮想カードが使われた瞬間、発行パートナーからの
authorization webhook に対して承認/拒否を返す。

**厳しい制約**: 発行パートナーの webhook タイムアウトは概ね **1〜2 秒**（パートナーにより異なる）。
超過時の挙動（既定承認 / 既定拒否）はパートナー側の設定で決まる。したがって:

- ASA ハンドラは**ポリシー評価のみ**を行い、外部呼び出しを一切しない
- ポリシーと残高はエージェント単位で事前展開しておく（Credits の Edge 設計と同型）
- **タイムアウト時の既定挙動を、テナントが明示的に選んで契約時に記録する。**
  暗黙の既定を持たない。§12。

> **決定事項**: Tier 2 は v1 の必須スコープに入れるが、**Tier 0 → 1 → 2 の順で提供する。**
> Tier 2 だけを最初に出すと、発行パートナー契約が導入の前提になり、営業サイクルが長くなる。

### 6.4 レール正規化

各レールの認可メタデータを共通形に落とす。

| 共通フィールド | x402 | ACP | AP2 | Card |
|---|---|---|---|---|
| `payee` | 支払い先アドレス / リソース | merchant | merchant | acceptor（加盟店） |
| `face_value` | payload の金額 | SPT の上限 | mandate の上限 | authorization amount |
| `maturity` | payload の有効期限 | SPT の失効時刻 | mandate の有効期限 | authorization の有効期間 |
| `mandate_ref` | payload hash | shared payment token id | mandate（VC）の id | network transaction id |
| `endorsement_chain` | — | — | mandate の委任連鎖 | — |

**未対応フィールドは埋めない。** 存在しないものを 0 や null で埋めると、監査時に
「本当に無かったのか、取れなかったのか」が区別できなくなる。`unavailable` を明示する。

## 7. Policy Engine

文法は `spec/policy.md` に規範として定義済み。本節は Wallet 固有の運用要件のみ。

### 7.1 ポリシーの階層

組織 → チーム → エージェント の3階層。**すべて交差で合成し、最も厳しい結果が勝つ**（D-10）。
上位が下位を緩めることはできない。「例外を認める」は上位ポリシーの変更でのみ行い、
その変更自体が register に残る。

### 7.2 既定ポリシー（新規エージェントの初期値）

| 項目 | 既定 |
|---|---|
| `per_action.max` | $50 相当 |
| `per_period` | `P1D` / $200 相当（rolling） |
| `aggregate.max` | 未設定（無制限）だが、`per_period` があるため実質有界 |
| `purpose.require` | `false`（Tier 0/1 では false、Tier 2 有効化時に `true` を推奨） |
| `ladder` | `auto` ≤ $50 → `notify` ≤ $500 → `counter_seal` |
| `degraded` | `deny` |

> **Credits と既定が逆になる点に注意。** Credits の degraded 既定は `allow`（顧客のプロダクトを
> 止めない）。Wallet の degraded 既定は `deny`（判断できないまま金を出さない）。
> 受け取る側と払う側で、失敗時に守るべきものが違う。この非対称は意図的である。

### 7.3 目的コード（`purpose`）

Master Doc §1.4-3「エージェントの経費規程」の中核。エージェントの支出を企業経理の語彙に翻訳する。

- 目的コードはテナントが定義する（例: `research`, `ads`, `infra`, `vendor-trial`）
- 会計科目・コストセンターへのマッピングを持てる
- `purpose.require = true` のとき、目的なしの支出は `policy_denied`

### 7.4 拒否の説明可能性

不渡り時のレスポンスは**どの規則が効いたか**を必ず含む。

```jsonc
{
  "decision": "dishonored",
  "reason": "policy_denied",
  "rule": {
    "policy_id": "eng-research-agents",
    "version": 3,
    "clause": "limits.per_period",
    "detail": { "window": "P1D", "max": 20000, "used": 19640, "requested": 800 }
  }
}
```

「拒否されました」だけを返すポリシーエンジンは運用できない。保有者はどの上限を上げるべきか
知る必要がある（`spec/policy.md` §4）。

## 8. Approval Ladder

### 8.1 動作

ラダーが `counter_seal` に到達した要求は `pending_seal` 状態で保留される
（`spec/authorization.md` §3 の規範状態）。保留中は**何も予約されない**。

```
request ──► pending_seal ──┬─► issued（quorum 到達）──► captured
                           ├─► dishonored（承認者が却下。reason=policy_denied）
                           └─► expired（timeout 経過）
```

- 承認先: Slack / Web / API。**メールは v1 では通知のみで、承認導線にしない**（なりすまし耐性）
- `quorum` に達するまで保留。承認者・時刻・手段は register に記録
- `timeout` 経過で自動失効（既定 4 時間）

### 8.2 エージェントを待たせない（US-03 / US-08）

承認待ちで長時間ブロックするのは Eng 側の導入拒否理由になる。したがって:

- authorize は即座に `pending_seal` を返す。**同期で待たせない**
- エージェントは webhook / ポーリングで結果を受け取り、タスクを再開する
- SDK は「保留 → 再開」を扱うヘルパを提供する（仕様のみ、実装は Phase 2）

### 8.3 承認疲れへの対処

- 同一エージェント × 同一 payee × 同一目的の反復承認は、`auto` への昇格を提案する
  （提案するだけ。自動では変えない）
- 承認要求のバッチ表示。1件ずつ通知しない
- 承認率が 95% を超えるラダー段は「実質機能していない」として警告する

## 9. Audit Trail

### 9.1 Register の共有

`spec/register.md` をそのまま使う。Wallet 固有の点のみ:

- `delta_amount` は通貨の最小単位、`currency` 必須
- `delta_cost_micro_usd` は使わない（0）。原価概念は受け取る側のもの
- `meta` に `payee`, `purpose`, `rail`, `mandate_ref`, `agent_id`, `drawer` を格納
- `counter_seal` の承認・却下は `kind=event` の register エントリとして記録する
  （`meta.event = seal_approved | seal_rejected`、承認者・時刻・手段を含む）。
  同一 `authorization_id` に対して要求側と承認側の両エントリが並ぶことが「割印」の実体

### 9.2 監査で答えるべき4つの質問

UI とエクスポートは、この4問に1画面で答えられなければならない。

1. **誰が** — どのエージェントが（`agent_id` / `handle`）
2. **誰の認可で** — どの振出人の権限に基づき、どの裏書連鎖を経て（`drawer` / `endorsement_chain`）
3. **何のために** — どの目的コード・どのタスクで（`purpose` / `meta.task_ref`）
4. **いくら** — 額面と確定額、どのレールで（`face_value` / `captured_amount` / `rail`）

### 9.3 オフライン検証

`spec/register.md` §5–6 のハッシュチェーンと署名ルートにより、テナントは TEGATA に依存せず
エクスポートの完全性を検証できる。**これは機能ではなく、この事業の前提条件である**
（Master Doc §3.1「金を扱うコードは監査可能性そのものが購買理由になる」）。

## 10. Spend Analytics

| ビュー | 内容 |
|---|---|
| **Agents** | エージェント別の支出・拒否率・承認待ち時間・予算消化率 |
| **Purposes** | 目的コード別。会計科目マッピング付き |
| **Payees** | 支払い先別。新規 payee の出現をハイライト |
| **Rails** | レール別コストと手数料 |
| **Anomalies** | 異常検知（§10.1） |
| **Unattributed** | 帰属先不明の支出。**この数字を減らすことが Tier 0 の KPI** |

### 10.1 異常検知（v1 のスコープ）

機械学習を持ち込まない。説明可能な規則のみ:

- 新規 payee への初回支出
- 直近 28 日の日次中央値の N 倍（既定 5）を超える単日支出
- 通常時間帯外の支出（`schedule` を設定していないテナントにも観測として出す）
- 拒否の急増（侵害またはポリシー誤設定の兆候）

> 説明できない検知はアラート疲れを生み、無視されるようになる。無視されるアラートは無いのと同じ。

## 11. 非機能要件

| 指標 | 目標 |
|---|---|
| Tier 1 authorize p99 | < 100ms |
| Tier 2 ASA ハンドラ p99 | **< 300ms**（パートナーのタイムアウト 1–2 秒に対する安全余裕） |
| ASA ハンドラのタイムアウト率 | < 0.01% |
| 可用性（enforcement） | 99.95%/月 |
| Register 反映 | < 5s |
| 承認通知の到達 | < 10s |

- ASA ハンドラは**外部 I/O を持たない**。ポリシーと残高はメモリ上に事前展開する
- 冪等性・整合性モデルは `spec/authorization.md` §8–9 に準拠

## 12. 規制と責任境界（最重要）

Master Doc §5 Product B risk 3。設計判断として厳守する。

### 12.1 やらないこと

- 顧客資金を自社名義で保管しない
- 資金移動を自社で実行しない
- カードを自社で発行しない（BIN スポンサーを持たない）
- 「送金する」「資金を預かる」という表現をドキュメント・LP・UI で使わない（Master Doc §4.6-4）

### 12.2 やること

- 認可の判断とその記録
- 発行パートナー / カストディパートナーへの指示の中継
- 資金の所在と保全主体を UI 上で明示する（「残高は◯◯社が保全」）

### 12.3 タイムアウト時の既定挙動

Tier 2 で TEGATA が時間内に応答できなかった場合の挙動は、**発行パートナー側の設定**である。
テナントは導入時にこれを明示的に選択し、その選択を register に記録する。
TEGATA 側の `degraded` 設定と、パートナー側のタイムアウト既定が矛盾しないことを
導入時チェックリストで検証する。

> ここを曖昧にしたまま本番に出すと、障害時に「誰の判断で金が出たか」が答えられなくなる。
> それはこのプロダクトの存在意義の否定にあたる。

## 13. Open-core 境界

| OSS（AGPLv3） | クラウド |
|---|---|
| Policy schema と評価器 | hosted enforcement の SLA |
| Register 形式と検証ツール | 発行パートナー接続（Lithic / Stripe Issuing） |
| レールアダプタ（x402 / ACP / AP2 / card 正規化） | 承認ラダーの通知基盤（Slack 等） |
| Agent identity プリミティブ | Spend analytics / 異常検知 |
| | Tier 0 の取り込みコネクタ群の保守 |

**レールアダプタを OSS に置くことが Switzerland position の実装**である。
どのレールにも肩入れしていないことは、コードが公開されていて初めて信用される。
