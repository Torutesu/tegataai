# セキュリティレビュー — Credits MVP

2026-08-21 / 公開前レビュー / 対象: `packages/` 全体と `site/`

> 実施理由: 公開すればこのサーバは**クレジットを発行する**。発行を誰に許すかが
> 最も高くつく間違いになる。

---

## 1. 発見した脆弱性

### S-01（重大・修正済み）— Stripe webhook の認証バイパス

**症状**: `stripe-signature` ヘッダを**省略するだけ**で署名検証が丸ごとスキップされていた。

```js
// 修正前
if (secret !== null && typeof sig === 'string') {
  verifyStripeSignature(...);   // ← ヘッダが無ければ「検証しない」
}
handleStripeEvent(...);          // ← そのまま実行される
```

**影響**: テナント ID（秘密ではない。bootstrap が標準出力に印字する）を知っていれば、
誰でも偽の `invoice.paid` を投げて**クレジットを無制限に発行できる**。
このシステムで起こりうる最悪の欠陥そのもの — 無からの資金創出。

**修正**: 検証を必須にした。以下はすべて `401`:
- 未知のテナント
- webhook secret が未設定のテナント
- 署名ヘッダの欠落

未知のテナントと署名欠落で**同じ応答**を返すため、テナント ID の存在を探る用途にも使えない。

### S-02（中・修正済み）— 署名を再シリアライズしたボディに対して検証していた

**症状**: `verifyStripeSignature(JSON.stringify(raw), ...)` — パース済みボディを
**再度 JSON 化**したものに対して検証していた。署名は**送信されたバイト列**に対するもので、
再シリアライズは空白もキー順も保存しない。正しい署名を偽と誤判定しうるし、
逆にバイト列と一致しないものを通す余地も残る。

**修正**: `addContentTypeParser` で生のテキストを保持し、**送られてきたバイトそのもの**に対して
検証する。テストは意図的に空白を含むボディで、再シリアライズ方式では通らない形にしてある。

### S-03（低・修正済み）— 動的な SQL 列名

**症状**: `updateTenant` が `patch` のキーを SQL に**文字列として**埋めていた。
現在の呼び出し元はすべてリテラルなので実害はないが、リクエスト由来の値が
一度でも流れ込めば注入経路になる。

**修正**: 書き込み可能な列名を集合で固定し、それ以外は例外にした。
テストは列名に `DROP TABLE register; --` を仕込んで、register が残ることを確認している。

## 2. 確認して問題なかったもの

| 項目 | 結果 |
|---|---|
| テナント分離 | 別テナントの鍵で同名 subject を引くと 404、エクスポートにも現れない（テスト済み） |
| 認証をすり抜ける経路 | `/health` と webhook のみ。パス走査（`/v1/webhooks/../register/export`）も 401/404（テスト済み） |
| 秘密の漏洩 | 応答本文に `sk_*` / `whsec_*` / `secret_key_hash` が現れないことをテストで確認 |
| 鍵の保存 | 平文を保存せず SHA-256 のみ。bootstrap は一度だけ表示し、二度と出せないと明記 |
| 冪等キーのスコープ | `(tenant_id, idem_key)` の主キー。他テナントのキーと衝突しない |
| SQL パラメータ化 | S-03 の1箇所を除き全て束縛パラメータ |
| 台帳の改竄 | UPDATE / DELETE をトリガで拒否。エクスポートは外部検証可能 |
| Stripe 署名の比較 | `timingSafeEqual`、長さ不一致も先に弾く |
| リプレイ | タイムスタンプ許容窓 300 秒 + `stripe_event.event_id` の一意制約 |

## 3. 既知の限界（修正せず、明記する）

| # | 内容 | 判断 |
|---|---|---|
| ~~L-1~~ | ~~レート制限がない~~ | **解消**。PRD §12.6 のとおり実装（テナント 1,000 rps → 429、Subject 20 rps → **不渡り** `rate_limited`）。単一ノードのメモリ内トークンバケットであり、分散化は Q-33 と同じ課題として据え置き |
| L-2 | `/v1/register/export` が全件をメモリに載せる | 自テナントのデータなので自傷に留まる。ストリーミング化は台帳が大きくなってから |
| L-3 | API キーが1本・ローテーションなし | MVP スコープ外。漏洩時は bootstrap のやり直しになる |
| L-4 | ブラウザからの直接呼び出し不可（CORS なし） | **意図的**。MVP はサーバ間のみ。publishable key + Subject JWT は後続（PRD §12.4） |
| L-5 | webhook のテナント指定が `Tegata-Tenant` ヘッダ | 署名が本体の認証なので、ヘッダは宛先指定にすぎない。将来はテナントごとの URL に分ける |
