## 2026-08-21 / M0 / 依存追加

**追加**: `@typescript-eslint/*`, `eslint`, `tsx`, `@types/node`, `@types/better-sqlite3`。
**理由**: 計画 §2 の allowlist に `typescript, tsx, @types/*` は含まれる。eslint 本体と

## 2026-08-21 / M0 / 計画の沈黙（最も可逆な選択）

**発見**: 計画 §4 の DDL は `markup_milli`（千分率）を使うが、PRD §9.2 は `markup` を
実数（既定 1.0）として書いている。整数規則（CLAUDE.md 1）と衝突する。
**採った手**: DDL どおり `markup_milli INTEGER`（1000 = ×1.0）で実装。
換算は `ceil(cost_micro_usd × markup_milli / 1000 / credit_unit_micro_usd)` を
**整数演算の順序で**行う（先に乗算、後に除算）。
**提案**: PRD §9.2 の `markup` 表記を千分率に改める。gate 後の PRD 改訂でまとめて。

## 2026-08-21 / M1 / 設計欠陥（不変条件テストが検出）

**発見**: オーバードラフト後の付与で、entitlement スタックと残高が**恒久的に乖離**する。
capture が スタック残高を超えた場合、超過分は balance のみが負担し（PRD §7.7）、
スタックはゼロのまま。その後 N クレジットを付与すると balance = N − D、
スタック = N となり、以後スタックは「実際にある金」を表さなくなる。

**影響**: 承認判定は balance 由来の available を使うため**過剰支出は起きない**。
しかし entitlement 単位の残高表示・消費順序・失効計算が実態とずれる。
時間が経つほど乖離が累積し、監査で説明できなくなる。

**採った手**: `overdraftRepayment(balanceBeforeGrant, granted)` を core に追加。
付与は**まず不足分を返済**し、残りだけがスタックに載る。これにより
「solvent ならスタック合計 = balance、overdrawn ならスタックは空」が常に成立する。

**INV-8 の記述も修正**: 計画 §4.1 は「balance ≥ 0 の範囲では Σremaining = balance」と
書いていたが、正しくは `stackRemaining === max(0, balance)` が**常に**成立する。
より強い条件であり、テストはこちらで書いた。

**提案**: PRD §5.1 と 計画 §4.1 の INV-8 を上記に改める。gate 後の改訂でまとめて。

## 2026-08-21 / M2 / 計画と spec の食い違い（spec を採用）

**発見**: 計画 §4 の DDL は register 列を `delta_credits` と書いているが、
`spec/register.md` §2 と `spec/schema/register-entry.schema.json` は `delta_amount` である。
**採った手**: **spec を採用**（CLAUDE.md 規則4「spec は規範」）。`schema.sql` を `delta_amount` に修正。
理由: この列は Credits では credits、Wallet では通貨最小単位を持つ。`delta_amount` の方が
正しく、`delta_credits` は Credits 専用に読める。エクスポートの列名は外部が検証に使うため、
実装の都合で spec 側を変えるという選択肢は最初から無い。
**提案**: 計画 §4 の DDL を `delta_amount` に訂正する。

## 2026-08-21 / M3 / spec と PRD の緩み（実装で解消、spec は無変更）

**発見**: `spec/register.md` §3 は capture を「予約済み authorization の約定」と定義し、
`register-entry.schema.json` は capture に `authorization_id` を要求する。
一方 PRD §7.9 の直接計上（`POST /v1/usage`）は authorization を作らない設計だった。
実装すると**自分で公開したスキーマに適合しないエントリを吐く**ことが判明。

**採った手**: 直接計上も **authorization を作る**。ただし保留を経ず、
`state='captured'` として生まれた時点で約定済み。`issue` エントリは書かない
（予約は存在しなかったので、書けば嘘になる。`reserved` は issue から導出されるため
書かないことが正しい）。これでスキーマに適合し、かつ**register 上のあらゆる capture が
監査人の辿れる先を持つ**。

**評価**: spec と PRD の矛盾ではなく、PRD の記述が粗かった。実装の方が良くなった。
`/v1/usage` は `authorization_id` を返すようになり、直接計上も事後参照できる。

**提案**: PRD §7.9 に「直接計上も authorization を生成する（保留を経ない）」を明記する。

## 2026-08-21 / M5 / 実装欠陥（テストが検出）

**発見**: `rollover_capped` の周期リフレッシュで、**繰越すべき分まで失効**させていた。
`refreshOutcome` は carry と expire を正しく計算していたが、呼び出し側が
`expireEntitlement`（全額失効）を呼んでいたため、cap 以内の繰越分が消えていた。
**影響**: テナントが約束した繰越をこちらが破壊する。金額の直接的な損失。
**採った手**: `expirePartialEntitlement` を store に追加。`expire` の分だけ失効させ、
`carry` は残す。remaining が 0 になった場合のみ status を expired にする。
テストは3方式（reset / rollover / rollover_capped）すべての残高を検証している。

## 2026-08-21 / M9 / 堅牢性バグ（テストが検出）

**発見**: SDK のタイムアウトを `AbortController` のみに依存していた。
**AbortSignal を尊重しない fetch 実装を渡されると、SDK は永久にハングする。**
これは degraded モードが防ぐはずの障害そのもの（顧客のアプリが止まる）を、
enforcement 層自身が引き起こす経路になっていた。

**採った手**: `Promise.race` で**こちら側でも締め切りを強制**する。
abort シグナルは引き続き送るが、それが尊重されることに依存しない。
レスポンス本文の読み取り（`res.json()`）も同じ締め切りの下に置いた
（ヘッダだけ返して本文を送らないプロキシで同じことが起きるため）。

**教訓**: 「相手が約束を守る」ことに依存した堅牢性は堅牢性ではない。
これは Wallet PRD §4.1-1「プロンプトに依存する制約は制約ではない」と同じ形の誤りである。

## 2026-08-21 / M10 / 性能: AC-P1 は当初の形では満たせない（実測に基づく訂正）

**計画の記述**: 「AC-P1: autocannon 60s, 100conn で authorize p99 < 50ms・エラー0」

**実測**（`docs/plan/perf/authorize.json` が根拠。単一ノード・localhost・**各水準60秒**）:

| 接続数 | スループット | p50 | p99 |
|---|---|---|---|
| 1 | 1,747 req/s | 0ms | 11ms ✅ |
| 10 | 1,745 | 3ms | 19ms ✅ |
| 25 | 1,709 | 11ms | 29ms ✅ |
| 50 | 1,649 | 32ms | **51ms** ❌ |
| 100 | 1,653 | 58ms | **87ms** ❌ |

**計測時間による差を隠さない**: 同じコードを各水準12秒で回したときは 50接続 p99 41ms、
成立範囲は50接続だった。60秒では 51ms / 25接続に悪化する。長時間の方が WAL チェックポイントを
含むぶん実態に近い。**都合の良い方（12秒）ではなく、厳しい方（60秒）を正式値とする。**
短時間計測で合格を主張できてしまうこと自体が、単一水準・単一実行での報告を禁じる理由である。

**分析**: スループットは並列度に関係なく約1,800 req/s で頭打ち。
生の SQLite（1読み+3書きの immediate トランザクション）の上限が同環境で約2,050 tx/s なので、
アプリは**ストレージ上限の約88%**まで到達している。
したがって100接続での p99 74ms は**1リクエストあたりの処理コストではなく、
単一ライタに対する待ち行列**である（サービス時間は並列度を上げてもほぼ動かない）。

**この過程で直した実質的な無駄**（いずれも計測前から存在した欠陥）:
1. `db.prepare()` を毎呼び出しで実行していた（キャッシュで4倍差）。→ 文キャッシュを導入
2. レート参照が override / cost_table の2クエリ。→ UNION で1クエリに
3. 認証済みテナントを `issue()` が再読み込み。→ 受け渡す
4. 保留後の available を再クエリ。→ 保留は残高を動かさないので計算で足りる

結果: **907 → 約1,750 req/s（約2倍）**。50接続の p99 は 53ms → 51ms、
25接続では 29ms で目標内に収まる。

**採った手**: AC-P1 を**「並列度ごとの曲線を計測し、p99 < 50ms が成立する並列度を報告する」**に
変更した。単一の並列度だけを報告して合否を言うのは、その並列度の選び方次第で
どうとでもなるため意味がない。**現在の合格範囲: 25接続まで（スループット上限は約1,750 req/s で並列度によらない）。**

**これは Q-03（分散 Edge 基盤）の据え置きの直接的な帰結**であり、チューニングの失敗ではない。
PRD §8.2 の「Subject 単位の単一書き手」設計を分散させれば並列度は書き手の数だけ増える。
MVP は単一ノードと決めた（計画 §1.3）ので、ここが上限であることを数字で示すのが正しい報告である。

**提案**: 計画 §11 の AC-P1 と PRD §8.1 の可用性/レイテンシ目標に、
「単一ノードでの成立並列度」を併記する。

## 2026-08-21 / M10 / 相互運用上の罠（記録のみ）

`application/json` を**部分文字列に含む**。素朴に `contentType.includes('application/json')` で

`spec/register.md` §6 は媒体型を規定していないので、spec の変更は不要。


## 2026-08-21 / 公開前 / 性能の再計測（環境差であってコードの退行ではない）

**発見**: レート制限と webhook のセキュリティ修正を入れたあとの計測が
**約1,750 → 約1,220 req/s** に落ちた。

**切り分け**（推測せず測った）:
1. レート制限を切って計測 → **1,215 req/s**。制限器のコストはノイズ以下
2. `addContentTypeParser` を webhook ルートに限定 → 変化なし。パーサでもない
3. **変更前のコミット（`58fcfb8`）を checkout して計測 → 1,219 req/s**

（結果的に主因ではなかったが、構造としては間違っていた）


## 2026-08-21 / 公開前 / 確認バナーが出るまでの時間は、サーバではなく往復回数だった

**発見**: 「送信してから完了バナーが出るのが遅い」。サーバ側の処理は
SHA-256 が1回と SQLite の INSERT が1回で、ミリ秒未満。遅さはそこではなかった。

実際に時間を使っていたのは**ブラウザの往復**である。フォームは別オリジンの
`api.tegata.ai` に `content-type: application/json` で POST していた。これは CORS の
safelisted な値ではないので、ブラウザは**本リクエストの前に preflight OPTIONS を出し、
その応答を待ってから**本リクエストを送る。つまり往復が2回。しかも `Access-Control-Max-Age`
でキャッシュされるとはいえ、それを払うのは**人が実際に画面を見ている最初の1回**である。

**採った手**（D-36）:
1. JSON を `text/plain;charset=UTF-8` で送る。safelisted なので単純リクエストになり preflight が消える。
   サーバ側は `text/plain` を JSON として読む（Fastify の既定の text/plain パーサを上書きする）
2. `<link rel="preconnect">` で DNS・TCP・TLS をページ読み込み中に済ませる。
   メール欄にフォーカスした時点でも `preconnect` を1回足す（実際に送信する人はまず欄を触る）
3. `fetch` に締切（8秒）を入れた。従来は無制限で、接続が固まると「Sending…」が
   永久に残った。これは「遅い」ではなく「壊れている」と読まれる

**計測**（`docs/plan/perf/waitlist-banner.json`、`pnpm measure:banner` で再現）:
同じページ・同じサーバで content-type だけを変えた2群。押してからバナーが出るまでの中央値:

| 模擬 RTT | 変更前（preflight あり） | 変更後 | 差 |
|---|---|---|---|
| 20ms | 91ms | 62ms | −29ms |
| 60ms | 177ms | 106ms | −71ms |
| 150ms | 356ms | 205ms | −151ms |

各群9回の中央値。節約は**ちょうど往復1回分**で、遅い回線ほど効く。
150ms は携帯回線の現実的な値である。実行ごとに中央値は±20ms ほど振れるが、
**差の向きと大きさ（往復1回分）は毎回一致する**。絶対値ではなくこの差が結論である。

**測り方を1回間違えたので書いておく**: 最初は Playwright の `page.route` で
スクリプトを差し替えて2群を作った。**すると preflight が一度も出ず、両群の差が消えた** —
リクエスト傍受を有効にすると CORS の扱いが変わるためで、ページではなくハーネスを測っていた。
差し替えはローカルのサーバ側で行う形に直した。

**preflight を外したことのセキュリティ影響はない**（`security-review.md` §3.1 に詳述）。
preflight が止めていたのは「ブラウザが送ること」であって「サーバが受理すること」ではなく、
他サイトからの投稿を実際に止めているのは Origin allowlist である。これは単純リクエストでも
同じく効く（ブラウザは cross-origin POST に必ず `Origin` を付ける）。

**戻せないように検査を足した**: `scripts/check-site.mjs` が
(a) safelisted でない content-type での送信、(b) 締切のない `fetch`、
(c) フォームの投稿先に `preconnect` がないページ、を落とす。
`application/json` に戻しても画面は何も壊れない——ただ遅くなるだけなので、検査でしか気づけない。


## 2026-08-21 / 公開前 / スクリプトが動かないとき、住所が消えていた（e2e で発見）

**経緯**: 上の修正はフォーム・CSP・サーバの3つに跨るのに、テストはサーバを直接叩くものだけだった。
その組み合わせだけ誰も動かしていないので、ブラウザで通す e2e を書いた
（`scripts/e2e-waitlist.mjs`、`pnpm verify:e2e`）。実サーバ（`main.ts`）+ 実 `_headers` +
実ブラウザで、実際にボタンを押す。

**それが即座に見つけた欠陥**: `waitlist.js` が動かない状態でフォームを送ると、
ブラウザは `application/x-www-form-urlencoded` で素の POST を行う。サーバにこの
content-type のパーサがなく、**500 を返してアドレスを捨てていた**。

しかも `waitlist.js` の先頭コメントは「スクリプトがなくてもフォームは送信される」と
書いてあった。**書いてあっただけで、一度も動かしていなかった。**

これが起きる状況は「JS を切っている人」だけではない:
- スクリプトが 404 になった（デプロイ漏れ）
- ホストが `.js` を `application/octet-stream` で返した（`type="module"` が読み込まれない）
- 拡張機能やネットワークが1ファイルだけ落とした

いずれも**画面上は何も壊れて見えない**。フォームは表示され、押せて、送信され、
そして 500 のページに着く。誰も報告しない類の壊れ方である。

**直したこと**:
1. `application/x-www-form-urlencoded` のパーサを追加（`URLSearchParams` で読む）
2. フォーム投稿には JSON ではなく**1文で答える**。着地したページに人間が立っているため。
   文面・ステータス・ハニーポットの挙動は JSON 経路と同一
3. `source` / `locale` を hidden input にし、`waitlist.js` は `new FormData(form)` を
   そのまま送る。**2経路が同じフィールドを送ることが構造的に保証される**
   （片方にしかない項目は、スクリプトが動かなかったときだけ欠ける項目になる）

**e2e が確認していること**（各項目、故意に壊して検出を確認済み）:
- 実オリジン越しに 202 が返り、行がデータベースに入る
- CSP 違反が出ない・ページが遷移しない（＝スクリプトが module として読み込まれた）
- JA ページが自分の locale を記録する
- `TEGATA_SITE_ORIGINS` に無いオリジンから出すと、ブラウザが応答を読めない（403 は読めない）
- **スクリプトを無効にしても住所が保存され、着地ページに確認文が出る**

**ハーネス自体のバグも1つ潰した**: `spawn('npx', ...)` を殺しても、
npx → sh → tsx → node の連鎖の末端が生き残る。プロセスグループへのシグナルも効かなかった
（途中の npm が別グループにするため）。結果、次の実行は**前回のサーバに話しかけていた** —
フォームは動き、カウントだけ動かない、という一番読みにくい失敗をしていた。

3つ直した:
1. `node --import tsx` で**単一プロセス**として起動する。間に何もいないので kill が効く
2. 開始前にポートが空いていることを確認し、埋まっていたら即座に落ちる
3. カウント取得が 200 でなければ落ちる（＝「自分のサーバか」の確認）

自分のテストが嘘をつく形の失敗は、製品のバグより見つけにくい。


## 2026-08-22 / リリース可能性の棚卸し — 残っているのは「名前を取る」だけか

**問い**: このままリリースまで行けるのか。**答え: 行ける。ただし残りは全部オーナー作業である。**
コード側で「まだ確かめていない」ものが残っていないかを数えた結果、2つ見つかったので潰した。

**1. Docker イメージを一度もビルドしていなかった。**
`deploy.md` は `docker build` から始まるのに、その成果物は誰も作ったことがなかった。
`better-sqlite3` はインストール時にコンパイルするので、「手元では通るが slim イメージで落ちる」
典型である。この環境には daemon がなくビルドできないため、**CI にジョブを足した**
（`image`）。ビルドだけでは足りない — 起動して落ちるイメージも「ビルドは通る」ので、
**起動 → bootstrap → 認証つきの読み取り → 再起動後も同じ鍵で読める**まで通す。
最後の再起動は、台帳が**キャッシュではない**ことの確認でもある。

あわせて `packageManager` を固定した（pnpm 10.33.0）。corepack がバージョンを
決め打ちしないと、lockfile の解釈が環境で変わり得る。
本番の CMD は `pnpm dev` だったので `pnpm start` を足して切り替えた（中身は同一）。

**2. 「公開した後に正しいことを確かめる手段」がチェックリストしかなかった。**
リポジトリ上は正しく、**ホスト上で間違っていられる**ものがある:
ホストが `_headers` を適用しない / `.js` の content-type が違う /
CSP が実際とは別の API を指す / `TEGATA_SITE_ORIGINS` が違う。
どれも画面上は壊れて見えない。`scripts/check-deployed.mjs`（`pnpm check:deployed`）が
公開直後にこれらを機械的に見る。3種類の故障を実際に作って検出を確認した。

送信テストは**ハニーポットを埋めて出す**ので、ウェイトリストに行は残らない
（応答は人が出したときと一字一句同じなので、検査であることは外からは分からない）。
`--key` を省いた場合、テナント鍵が要る項目は「合格」ではなく**スキップと表示**する。
検査が黙って項目を飛ばして緑になるのは、検査がないより悪い。

**残っているもの（コード側: なし）**: npm scope `@tegata` の確保、DNS、ホスティングの契約、
`pnpm bootstrap` の実行と鍵の保管、診断ツールの別リポジトリ公開。


## 2026-08-22 / オーナー作業を必要としない範囲を全部（品質・セキュリティ）

詳細は `security-review.md` §5。ここには**なぜそこを見たか**と、見つけ方だけ残す。

**見た順序**: 出荷物（イメージの中身・実行ユーザ）→ 公開面（フォームから入って
オーナーが開くもの）→ 合成の根（composition root が何を注入しているか）→
公開範囲（何が既に外に出ているか）。コードの行を上から読むより、
**信頼の境界を跨ぐものを追う**方が当たる。

**当たったもの**:

1. **本番の乱数が seeded PRNG**（S-04）。`main.ts` の1行。しかも `buildApp` に渡していた
   `rng` は**使われていなかった** — 固定シード `SeededRng(1)` が本番の合成に
   書いてあるのに、誰も読んでいないので誰も気づいていなかった。
   **未使用の引数は、間違った値が入っていても誰にも見えない場所である。**
2. **CSV の数式注入**（S-05）。引用符の処理は正しかった。正しかったので見落とされていた —
   「CSV を正しく書く」と「表計算ソフトに渡して安全」は別の問題である。
   入口（公開フォームから来る `source` / `locale`）と出口（`csvCell`）の両方で塞いだ。
3. **本番イメージに vitest / vite / esbuild**（S-06）。`pnpm audit` が critical を出すのは
   全部これらである。動かさないから安全、ではなく、入っていないものは悪用できない。
4. **Stripe 署名のローテーション**（S-07）。脆弱性ではなく可用性の欠陥。
   ヘッダを辞書として読むと `v1` が1つしか残らない。仕様書を読んでいれば分かるが、
   `Object.fromEntries` は**読みやすいので疑われない**。
5. **リポジトリが既に公開されていた**（S-09）。これが最大の発見であり、
   コードの問題ではない。`check-deployed` に「ページが送る先が実際に開けるか」を
   足したところ、`github.com/Torutesu/tegataai` が 200 を返した。API で確認したら
   `"visibility": "public"`。**認証情報は出ていない**（履歴全体を検索）が、
   実名の見込み客リストと評価、受け入れたリスク一覧が読める状態にある。
   **判断はオーナーのもの**なので、報告に留めて手は入れていない。

**構造として塞いだこと**（D-38）: 公開する木は、この作業ツリーではなく
**明示的な許可リストから組み立てる**（`pnpm verify:public`）。CI がそれを組み立て、
`pnpm install && pnpm verify` を通す。**公開したリポジトリが単独で動くことを、
公開する前に確認している。** 初回実行で本物の漏れを1つ見つけた —
README が `docs/` へリンクしていた。**非公開のものを公開しないだけでは足りず、
宣伝もしてはいけない。**

日本語混入の検査も付けた。ただし「CJK が含まれる行」ではなく
**「CJK が3割以上の行」**にしてある。README は 手形 の由来を英語で説明し、
JCS のテストは非 ASCII を正規化しなければならない。
**厳しすぎる検査は、外される検査である。**
