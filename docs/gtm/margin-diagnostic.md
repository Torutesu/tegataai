# 仕様 — Margin 診断ツール（Product A の無料フック）

Select KK / 2026-08-21 / v0.1
Master Doc §7 Backlog #5 / Gate 判定材料

> **これは製品ではない。** 製品への導線であり、gate の判定データを取る装置である。
> 製品コードとは独立させ、製品の実装を待たずに作れる状態にしておく。

---

## 1. 一行

Stripe の課金データと AI プロバイダの利用データを突き合わせ、
**「あなたのユーザーの何%が赤字か」**を返す。

## 2. 設計上の最重要判断

### 2.1 データをサーバーに送らない

**すべてブラウザ内で処理する。アップロードしない。** ファイルは `File API` で読み、
計算はクライアントで完結し、結果もローカルに留まる。

**理由**: このツールの最大の障壁は「顧客の課金データを見知らぬスタートアップに渡す」ことへの
抵抗である。技術的にそれが不可能な設計にすれば、障壁そのものが消える。
ヒアリング（`icp-interviews.md` §2.2 質問17）の承諾率が跳ね上がる。

**帰結**: サーバーは静的配信のみ。TEGATA 側にユーザーのデータは一切残らない。
したがって「何社が使ったか」も分からない。§6 でこれをどう扱うかを定義する。

### 2.2 送信しないことを、見れば分かるようにする

- ページ上に「データは送信されません」と書くだけでは不十分。信じる理由がない
- ソースを公開し、ネットワークタブで確認できる旨を明記する
- 可能ならオフラインでも動作することを示す（Service Worker で完全キャッシュ）

> Master Doc §4.4 の voice に従い、誇張せずに事実だけを書く。
> 「安全です」ではなく「送信していません。ネットワークタブで確認してください」。

## 3. 入力

| # | ソース | 形式 | 必須 | 取得方法 |
|---|---|---|---|---|
| 1 | Stripe: 顧客と請求 | CSV export | 必須 | Dashboard → Billing → Export |
| 2 | AI プロバイダ: 利用明細 | CSV / JSON | 必須 | 各プロバイダのコンソールから export |
| 3 | 突合キー対応表 | CSV | 任意 | Stripe customer id ↔ プロバイダ側の識別子 |

### 3.1 突合の現実

**最大の難所はここ。** プロバイダの利用明細には Stripe の customer id が入っていない。
現実には以下のいずれかしかない。

| 突合方法 | 前提 | 精度 |
|---|---|---|
| **A. ユーザー別 API キー / プロジェクト** | プロバイダ側をユーザーごとに分けている | 高 |
| **B. metadata / user 識別子** | リクエストに識別子を付けている | 高 |
| **C. 対応表アップロード** | 顧客が自分で作れる | 高 |
| **D. 按分（フォールバック）** | 何もない場合。利用量比で按分 | **低。推定であることを明示** |

> **決定事項**: D を使った場合、結果画面に「これは推定です」を出力の全箇所に付記する。
> 精度のない数字を断定的に出すと、ツールの信頼と製品の信頼が同時に失われる。
> Master Doc §4.4「仕様を語れるなら形容詞は要らない」の裏返しで、
> **語れない部分は語れないと書く。**

### 3.2 プロバイダ対応（初期）

Anthropic / OpenAI。この2つで ICP の大半を覆う。
それ以外は「汎用 CSV」モードで、列マッピングをユーザーに指定させる。

## 4. 計算

指標定義は **PRD §11.2 と完全に一致させる。** 一致していないと、
ツールで見た数字と製品で見た数字が食い違い、導入時に信頼を失う。

```
provider_cost(user, period)       = Σ (プロバイダ明細の当該ユーザー分)
recognized_revenue(user, period)  = サブスク: 期間按分（日割り）
                                  + トップアップ: 消費分の按分
                                  + プロモ付与: 0
gross_margin(user, period)        = recognized_revenue − provider_cost
negative_margin_user              = 直近30日 rolling の gross_margin < 0
```

**期間**: 既定は直近30日。ユーザーが変更できる。

**通貨**: 単一通貨のみ（多通貨は「対応していません」と明示して除外行を出す）。
為替を推測しない。

## 5. 出力

### 5.1 ヘッドライン（1つだけ）

```
あなたのユーザーの 14% が赤字です。
その 14% が、モデル費用の 61% を使っています。
```

**数字は2つまで。** 3つ以上並べた瞬間、どれも印象に残らない。

### 5.2 内訳

1. **粗利分布** — ユーザーを粗利順に並べたヒストグラム。赤字帯を明示
2. **上位コスト** — 最もコストを食っている 20 ユーザー（ID は伏せる / ローカル表示のみ）
3. **プラン別** — プラン別の平均粗利と赤字率
4. **除外行** — 突合できなかった / 通貨が混在した行の件数と金額。**隠さない**

### 5.3 出力の持ち出し

- PDF / PNG エクスポート（クライアント生成）。**社内共有されることが導線**である
- エクスポートには「TEGATA で計測」の控えめな署名を入れる（Master Doc §4.7 の証券的表記）
- CSV エクスポート（ユーザー別粗利）

## 6. 計測（データを送らない前提での）

送信しない設計を選んだ以上、通常のプロダクト分析はできない。代わりに:

| 取る | 方法 |
|---|---|
| ページ訪問数 | 静的配信のログ（アクセス数のみ、PII なし） |
| ツールを実際に使ったか | **測らない。** 代わりに §6.1 の自己申告導線を置く |
| 結果に対する反応 | §6.1 |

### 6.1 唯一の任意送信

結果画面に**任意**の1アクションだけ置く。

```
この結果について話しますか?  [ 30分の枠を取る ]
```

- 押した場合のみ、カレンダー予約に遷移する
- **数字は送らない。** 相手が面談で口頭で言う
- これがそのままヒアリング（`icp-interviews.md`）の獲得経路になる

> **gate 判定への寄与**: 訪問数に対する予約率が、この wedge の温度そのもの。
> ツールを使った人数が分からなくても、予約数は分かる。判定にはそれで足りる。

## 8. 作らないもの

- ログイン / アカウント作成（データを持たないので不要。摩擦だけが残る）
- Stripe / プロバイダの API 連携（OAuth を要求した時点で §2.1 の利点が消える）
- 継続モニタリング（それは製品の仕事。ツールは一回性の診断に留める）
- 改善提案の自動生成（数字を出すところまで。示唆は面談で人間が話す）
