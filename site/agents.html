A limit written into a prompt is a request, not a control

Somewhere in most companies running agents, one already has a payment method: a shared corporate card, someone's API key, a cap that exists only as an instruction. Instructions survive exactly as long as the agent behaves as expected.

The gap is rarely technical. It is that nobody wrote down who is answerable for what the agent spends. The template starts there, because every other delegation of spending authority in a company already has that paperwork.

What it makes you decide

An accountable name

One person per agent, the way a card has a cardholder. Not a team, not a mailing list. An agent with no named drawer does not get a payment method.

Delegation that only narrows

A sub-agent's limit never exceeds its parent's, its expiry never extends beyond it, and its categories are a subset. Revoking a parent revokes everything below it.

Which way it fails

Whatever sits between your agents and their money will be unavailable at some point. Deciding that during an incident is expensive in both directions.

Four audit questions

Which agent, whose authority, what purpose, how much. The template's last column asks where you would find each answer today — that column is the list of what to fix.

The machine-readable form of the same structure

The template is prose because a policy has to be readable by the people who own it. The same grammar is specified for enforcement, and both are open.

{ "policy_id": "eng-research-agents", "version": 3,
  "limits":   { "per_action": { "max": 500 },
               "per_period": { "window": "P1D", "max": 20000 } },
  "purpose":  { "require": true, "allowed": ["research", "eval"] },
  "ladder":   [ { "up_to": 1000,  "decision": "auto" },
               { "up_to": 10000, "decision": "notify" },
               { "decision": "counter_seal", "approvers": ["role:finance"] } ],
  "degraded": "deny" }

Counter-seal — two parties sealing across the same instrument, neither sufficient alone. Policies compose by intersection, so the most restrictive one wins and there is no override to reason about.

What we are not doing

We are not building the software for this yet, and we would rather say so than collect addresses for a waiting list. The evidence we can find says the problem is real and widely feared, but that very few companies are currently letting agents pay outside vendors at any scale — and where they are, the platform being bought from usually ships the controls already.

So the template and the schema are published for anyone who needs them today, and the product we are actually building is on the other side of this site.
